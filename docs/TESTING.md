# Testing

All fixtures are synthetic. No real calendar names, email addresses or events may be committed.

| Layer | Runs where | What it covers |
|---|---|---|
| unit | CI (Linux) | Time zones: Tokyo to Manila (minus 1 hour); all-day events never shifted; floating times labelled. Free-time interval arithmetic. Confirm tokens: single use, 5-minute TTL, bound to the exact change. Error mapping. Untrusted-text wrapping |
| fixtures | CI | Synthetic `.ics` files under `tests/fixtures/`: weekly series created in Asia/Manila; series with one edited occurrence (RECURRENCE-ID) and one deleted (EXDATE); multi-day all-day event; floating-time event |
| contract | CI | One suite run against the `fake` backend and the `caldav` backend. The CalDAV backend runs against a local Radicale server started in the CI job, so no iCloud account is needed (test tool only, not distributed). **Radicale passing does not prove iCloud compatibility** (python-caldav's docs don't mention iCloud); the opt-in integration run against your own iCloud `TEST` calendar is a launch requirement |
| auth (hosted) | CI | Unauthenticated request gets **401 with `WWW-Authenticate: Bearer resource_metadata=...`** (a header on a 200 is ignored by Claude); metadata `resource` equals the server URL exactly; token for a different GitHub user is rejected (FastMCP has no built-in allow-list, so this is our code); `/token` accepts form-encoded bodies and returns `invalid_grant` on a bad refresh token; PKCE S256 required. Checked with the MCP Inspector and then as a custom connector in Claude |
| Swift | CI (macOS) | `swift build` and `swift test` for helper JSON encoding and recurrence mapping. Runners have no Calendar access, so EventKit calls are not exercised |
| integration | **your Mac only**, opt-in | `pytest -m integration --calendar TEST` against EventKit |

## Integration test safety rules
1. Refuses to run unless the target calendar is named exactly `TEST`.
2. Creates events with UID prefix `icmcp-test-` and records every UID it creates.
3. Deletes only UIDs created in the same run, one at a time, through the same preview then confirm path.
4. Never calls delete without an ID. Never touches any other calendar.
5. Flow: create preview → confirm → verify by re-read → update (this occurrence, then whole series) → delete preview → confirm → verify gone.

## Status (2026-10-21)
- Built and passing in CI: unit tests (time zones, free time, service, MCP layer, converters, secrets and error mapping) and contract tests of the CalDAV backend against a local Radicale server (recurring series with an EXDATE and a moved occurrence, multi-day all-day, floating, Manila-to-Tokyo display, unreachable server, no URL or credential leakage).
- The contract suite runs against the CalDAV backend only; the fake backend is covered by the service and MCP-layer tests (a single parametrised suite across both is not done).
- Auth tests (M3), run with fake credentials: discovery documents, redirect allow-list, form-encoded `/token`, owner-only verifier, per-tool check, real-HTTP tests (owner sees and calls tools, another account sees none, bad token rejected), settings validation, CLI refusals (no auth config, `--dev-no-auth` with a public URL or non-loopback host, `--allow-writes` not yet available).
- Cloud Run support tests: OAuth state is ciphertext at rest and survives a restart (file store and a Firestore-style store, via `/register` then a rebuilt provider), a wrong key reads as missing, `PORT` is honoured, and `deploy.sh` is run against a fake `gcloud` that records commands and stdin (secrets reach Secret Manager over stdin only and never appear in a command line or output; deploy flags and least-privilege roles are asserted). This does not prove Google accepts the real flags.
- CI also builds the container image and checks it refuses to start unconfigured, runs as a non-root user, and holds no secrets.
- Not yet built: write and confirm tests (M4), mail tests, Swift helper tests. Not yet run: real GitHub sign-in, real iCloud, real Claude or ChatGPT connections.
- Real iCloud (2026-10-22): `scripts/probe_icloud.py` ran read-only from the developer's Mac and passed. Counts only: 6 event calendars; 35 events in the next 14 days (29 recurring occurrences, 0 all-day, 0 floating, 0 free/transparent, 0 with an override or exception); time zones Asia/Tokyo and Asia/Manila. Listing calendars took 8.2 s and the event search 2.9 s from the Mac, so the first tool call after a cold start can be slow. The account had no all-day, floating or exception events, so those paths are covered only by the fake-data tests.
- Cold start on Cloud Run (2026-10-22, revision 00003): 6.8 s for one sample after disabling FastMCP's startup update check (was 22.6 s). A second, real cold start (Claude's first request) took 22.6 s, with imports alone at 14.4 s, so cold starts vary a lot and can exceed Claude's 10 s limit for OAuth endpoints. Fallback options are in the project plan (Cloud Scheduler warm ping, lazy imports, `--min-instances 1`).
- Real Claude connection (2026-10-22/23, claude.ai custom connector): sign-in through GitHub works and `search_events` returned the real calendar. Two bugs found by this and fixed in commit `df588d9`: Firestore rejected Claude's URL-shaped client ID as a document name, and an expired GitHub refresh token became a 500 instead of a clean re-sign-in. Root cause of the second was GitHub "Token expiration" being on for the OAuth App; it is now opted out (see RUNBOOK-DEPLOY.md section 3).
- Write tools (M4, 2026-10-23): built and tested without touching real iCloud. Unit tests cover the confirm token (random, single use, five-minute expiry, tamper check, 10 confirmations per 10 minutes), gating (writes off, allow-list, re-checked at confirm time), the scope question for repeating events, conflicts, the re-read verification (each safeguard was checked by removing it and watching a test fail) and the MCP layer (tools absent when writes are off, annotations, instructions). Contract tests run create, update (one occurrence and the whole series), delete (one occurrence and the whole series), all-day, Manila-to-Tokyo display, an existing moved and deleted occurrence, and conflicts through a local Radicale server.
- Real-iCloud writes (2026-10-23): `tests/integration` (opt-in, `-m integration`, refuses unless a calendar named exactly `TEST` exists, deletes only what it created) **passes 5 of 5** against the real iCloud `TEST` calendar: create, update and delete a timed event, an all-day event, and a weekly series (move one occurrence, change reminders for the whole series, delete one occurrence, delete the series). `TEST` was left empty.
- **Bug found by that run, affecting reads too:** iCloud answers python-caldav's UID query (`event_by_uid`, and `search(uid=...)`) with `412 Precondition Failed` for every event, so `get_event` could never have worked on real iCloud (the earlier probe only listed and searched). Events are now fetched by address (the address seen in a search, then `<UID>.ics`, then a scan of the calendar). Regression tests simulate the 412.
- Still untested against real services: ChatGPT, write tools on iCloud, Mail.
